### P0-3：烧录后MAC是否变化 — ⚠️ 需要修正63端理解

**63端文档原文：**
> "重新烧录固件 → NV分区可能被擦除，MAC会重新生成"

**21e端实际情况：**

BS21E Flash分区表（来源：bs21e-standard.json）：

| 分区 | Item ID | 起始地址 | 大小 | 说明 |
|------|---------|---------|------|------|
| flashboot | 0x00 | 0x1000 | 40KB | 引导程序 |
| flashboot_backup | 0x01 | 0xB000 | 40KB | 引导备份 |
| **application** | **0x23** | **0x15000** | **544KB** | **应用固件** |
| **NV data** | **0x25** | **0xFE000** | **8KB** | **NV数据** |
| FOTA | 0x26 | 0x9D000 | 388KB | OTA升级区 |

**关键结论：NV分区（0x25）和application分区（0x23）地址完全独立。**

| 操作 | MAC是否变化 | tag_id是否变化 |
|------|-----------|--------------|
| 正常烧录application.bin | ❌ 不变 | ❌ 不变 |
| OTA升级 | ❌ 不变 | ❌ 不变 |
| 断电重启 | ❌ 不变 | ❌ 不变 |
| 恢复出厂设置 | ❌ 不变 | ❌ 不变 |
| **全量烧录（含NV分区）** | **⚠️ 会变** | **⚠️ 会变** |
| 手动擦除NV | ⚠️ 会变 | ⚠️ 会变 |

**正常开发流程中只烧录application分区，MAC和tag_id不会丢失。**

**但作为兜底方案，63端方案B仍然有价值：**
- 如果确实发生了全量烧录导致MAC变化
- 只要tag_id不变（NV同分区），63端可以通过tag_id匹配自动更新MAC
- 所以tag_id的NV持久化（P0-2）是关键保障

**21e端建议：双方都实现方案B作为兜底，但正常情况下不会触发。**

### P1-4：广播 qty 是否实时同步 — ✅ 实时同步

21e端代码流程：
```
收到0x10 → storage_sync_set_qty() → storage_sync_publish() → sle_slave_refresh_adv_payload()
```

`storage_sync_set_qty()` 更新qty后立即调用 `storage_sync_publish()` 刷新广播数据。
`refresh_adv_payload()` 内部：停广播 → 更新数据 → 重启广播，耗时约几十毫秒。

**结论：广播中的qty与内部qty几乎实时同步，延迟可忽略（<100ms）。63端可以放心使用被动扫描盘点。**

---

### P2-2：15秒报警后 status 自动恢复 — ✅ 需要修改，21e端确认修复

**当前问题：**
- 15秒后硬件定时器自动关闭蜂鸣器/LED
- 但 `status` 字段没有恢复为 0x00
- `seq` 也没有递增

**修复方案：**
在硬件定时器回调中增加：
1. `storage_sync_set_find_status(false)` → status恢复0x00
2. `storage_sync_publish()` → 刷新广播 + seq递增

**修复后行为：**
```
收到0x01 → status=0x01, 蜂鸣器+LED响
15秒后 → status=0x00, seq++, 广播自动更新
```

63端可通过扫描观察到 status 从 0x01 变为 0x00，确认寻物结束。

## 三、ESP32 交互补充

### 3.1 ESP32 在系统中的角色

```
┌──────────┐    JSON/串口    ┌──────────┐    SLE     ┌──────────┐
│  ESP32   │ ◄────────────► │  WS63    │ ◄───────► │  BS21E   │
│ 串口屏   │                │  Client  │            │  Server  │
└──────────┘                └──────────┘            └──────────┘
```

ESP32负责：用户交互界面（选区、添加数量、触发寻物）
WS63负责：SLE通信、映射表管理、协议转发
BS21E负责：标签数据存储、寻物执行

### 3.2 ESP32 操作流程

**入库操作（ESP32选区+添加数量）：**
```
1. 用户在ESP32屏幕上选择区域（如"A区"）
2. 用户输入物品名称（如"Type-C"）和数量（如50）
3. ESP32通过JSON发送给WS63：
   {"cmd":"stock_in","data":{"tag_id":1,"zone":"A","item":"Type-C","qty":50}}
4. WS63收到后：
   a. 更新映射表中tag_id=1的zone/item/qty
   b. SSAP Write [0x10, 0x00, 0x32] → BS21E（更新qty=50）
   c. NV持久化映射表
```

**出库操作：**
```
1. 用户在ESP32选择物品，点击出库
2. ESP32通过JSON发送给WS63：
   {"cmd":"stock_out","data":{"tag_id":1}}
3. WS63收到后：
   a. 更新映射表中tag_id=1的qty=0
   b. SSAP Write [0x10, 0x00, 0x00] → BS21E（更新qty=0）
   c. NV持久化映射表
```

**寻物操作：**
```
1. 用户在ESP32选择物品，点击寻物
2. ESP32通过JSON发送给WS63：
   {"cmd":"find_item","data":{"tag_id":1}}
3. WS63收到后：
   a. 查映射表获取tag_id=1的MAC
   b. 连接BS21E → SSAP Write [0x01] → 蜂鸣器响
```

**盘点操作：**
```
1. 用户在ESP32点击盘点
2. ESP32通过JSON发送给WS63：
   {"cmd":"inventory","data":{"zone":"A"}}（可选指定区域）
3. WS63收到后：
   a. 被动扫描：读取广播中的qty（秒级完成）
   b. 主动查询：逐个连接发送0x02（精确数据，2~3分钟）
```

### 3.3 ESP32与BS21E的关系

**ESP32不直接与BS21E通信。** 所有对BS21E的操作都通过WS63中转：
- ESP32 → WS63：JSON格式（串口/WiFi）
- WS63 → BS21E：SLE SSAP协议

BS21E端不需要关心ESP32的存在，只需要响应WS63的SSAP命令。

## 六、63端方案B兜底逻辑补充确认

63端提出的方案B：
> WS63扫描到广播 → tag_id匹配但MAC不匹配 → 自动更新映射表中的MAC

**21e端确认此方案可行，但需要补充一点：**

如果BS21E全量烧录后MAC和tag_id**都丢失**（tag_id回到0），则方案B无法匹配。此时WS63应将 tag_id=0 的设备视为"未配网"，需要重新配网。

```
WS63扫描逻辑：
  tag_id != 0 且 MAC匹配    → 正常使用
  tag_id != 0 且 MAC不匹配  → 方案B：自动更新MAC
  tag_id == 0               → 视为未配网，提示用户重新配网
```
